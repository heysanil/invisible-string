# The workflow editor

The workflow editor is a single focused column that reads like a delegation
memo, top to bottom: *when it happens* — the Trigger; *who handles it* — a
picker of the workspace's published Agents; and *what they should do* — the
Instructions, with `@` autocomplete sourced from the selected Agent's context
and the trigger's data.

Because a Workflow builds nothing, the header offers a **Run** popover to fire
it manually and an instant **Publish** — no build progress, no waiting; edits go
live the moment you publish them. If the bound Agent is republished without
something the instructions reference, the editor surfaces a staleness
diagnostic on the Workflow rather than letting a dispatch fail silently.

The header carries the Workflow's name as an inline-editable field — click it,
type, and Enter commits while Escape reverts, the same pattern the agent
editor uses for an Agent's name.

## Trigger

The Trigger section is five radio cards — Manual, Form, Webhook, Slack,
Schedule — and picking one expands its own draft-time configuration below the
cards. This section covers the editor's controls for each kind; for what each
trigger actually authenticates, resolves, and delivers, see
[Triggers](/docs/building/triggers).

### Manual

Manual needs no configuration at all. There's nothing to fill in — fire it
directly from the header's **Run** popover, covered below.

### Form

Form opens a field-schema builder. **Add field** appends a row, and each row
sets:

- **Label** — the text shown above the field on the rendered form.
- **Key** — the identifier the field is addressed by, `@trigger.<key>`.
- **Type** — Text, Long text, Number, Select, Checkbox, or Date.
- **Options** — a comma-separated list, required when Type is Select and
  disallowed otherwise.
- **Required** — a toggle; a submission missing a required field is rejected.

Rows can be reordered with the up/down arrows or removed with the trash icon.

### Webhook

At draft time, Webhook shows only a note: publishing mints a signing token,
and every field posted to it becomes addressable in the instructions as
`@trigger.<key>`. The live token lives in a separate **Ingress token** card
that only matters once the Workflow has been published — **Generate token**
mints the first one, and after that **Rotate token** replaces it, gated
behind a destructive confirmation since rotating immediately invalidates the
current token. Either action reveals the plaintext token exactly once, in an
amber card: "Copy this now — we store only a hash, so it won't be shown
again." A Copy button and the live ingress URL sit alongside it; after that
first reveal, only a status chip and the token's last four characters remain
visible.

### Slack

At draft time, Slack shows the routing rules you're setting — a "Channel id
(optional)" field, an "Only @mentions of the app" toggle, and an "Include
direct messages" toggle. A separate live binding card holds a Team select of
the workspace's connected Slack integrations plus a **Bind** (or **Update
binding**) button; once bound, the card shows a Bound status and a routing
summary. Editing the draft rules after binding doesn't change what's live —
the card warns "Routing rules changed in the draft — click Update binding to
apply them" until you push the update.

### Schedule

Schedule is a raw cron-string input — five fields, evaluated in UTC — with a
live human-readable preview underneath and a Valid or Unrecognized status
chip. New Workflows seed it with `0 9 * * 1` (09:00 UTC every Monday) as a
starting point. See [Triggers](/docs/building/triggers) for the cron grammar
itself.

## Choosing the Agent

The Agent section is a card radio-group of the workspace's published Agents
only — a draft that's never been published doesn't appear here, since a
Workflow can't dispatch to something that doesn't exist yet on the runtime.
Selecting a card grows an **Edit agent ↗** link into that Agent's own editor.

Three degraded states are designed rather than left to chance. If the
selected Agent's draft has since been unpublished, its card dims with a "Not
published" warning — "publish it in Agents, or pick another below." If the
selected Agent was deleted, its card dims to "Unknown agent" with a Missing
error chip. And if the workspace has no published Agents at all, the section
shows an empty state with an **Open Agents** link in place of any cards.

## Writing instructions

Instructions use the same rich-text editor as an Agent's persona, including
the plain-markdown toggle — see
[Personas and instructions](/docs/guides/personas-and-instructions) for the
shared writing guidance. A legend under the editor spells out the reference
vocabulary: type `@` to reference `@trigger.*` fields, the selected Agent's
connections, and `@skill.*`.

Typing `@` opens an autocomplete popup listing every reference currently
addressable, each with a right-aligned detail tag — form field, slack event,
webhook body, connection, or skill — naming its source. Arrow Up and Arrow
Down navigate the list, Enter or Tab accepts the highlighted entry, and
Escape closes the popup without inserting anything. Accepting a suggestion
inserts an atomic reference chip rather than editable text — it can be
deleted as a unit but not edited in place, and it serializes back to the
literal `@token` byte for byte. A reference typed inside a code fence is left
as plain text; it never becomes a chip.

A reference that doesn't resolve gets an amber underline and a warning
diagnostic naming exactly what's missing, for example
`@trigger.foo — No form field is keyed "foo".` or
`@skill.x — No attached skill is named "x" — attach it in Context.` Unlike a
hard error, an unresolved reference doesn't block publish by itself — see
Publishing below.

## Running it manually

The header's **Run** button opens a popover that dispatches through the same
route production ingress uses — a real run, not a preview. Its body adapts to
the trigger kind: manual and Slack triggers get a message textarea, form
triggers get the real rendered field inputs, webhook triggers get a JSON
payload textarea, and schedule triggers get no payload field at all — just a
"Fire the schedule" confirmation you submit with **Fire now**, since a
scheduled run always carries an empty message and lets the instructions
carry the whole task. Every other trigger kind submits with **Start run**.

Firing it this way always dispatches against the Workflow's current
*published* Agent version, never the draft. If the Workflow is unpublished,
or has changes since its last publish, an amber box replaces the submit
control — "Publish this workflow first — runs dispatch the published
version" — with a **Publish now** button inline, so there's no need to leave
the popover to unblock it. On success, the popover confirms "Run started"
with a **View in Chat ↗** link into the session it just created; see
[Sessions and runs](/docs/concepts/sessions-and-runs) for what happens from
there.

## Publishing

Publish validates the delegation, not just the syntax. Some checks run
locally the moment a section changes: trigger shape errors, "Choose an agent
to do the work" if the Agent section is empty, an error if the selected Agent
has no published version, "Instructions are empty — required to publish" if
that section is blank, and a warning for every unresolved `@` reference. Deeper
checks that need the server come back attached to the section they concern —
Trigger, Agent, or Instructions — by path, or to a general bucket when they
don't map to one section; every finding carries an "ask copilot to fix"
affordance that hands the issue straight to Copilot, see
[Copilot](/docs/building/copilot).

Severity decides what publish does with a finding: `error` blocks it,
`warning` doesn't. Publishing past a warning is a deliberate choice the
editor respects, not a bug it missed — with the one exception the agent
editor also makes: empty instructions read as a warning while you write, but
Publish stays disabled until the section has something in it.

Staleness is a related but separate signal. Because instructions can
reference the selected Agent's connections and skills, republishing that
Agent without something the instructions depend on surfaces a staleness
diagnostic on the Workflow — a warning against the Agent's *live* context,
not the context that existed when the instructions were written. Like any
other warning, it doesn't block publish; see
[Workflows](/docs/concepts/workflows) for why a Workflow deliberately carries
no context of its own to fall back on.

## Run history

Every run a Workflow's trigger starts — however it fired — lands in that
Workflow's run history and streams into Chat the same way a directly-started
conversation would; there's no separate workflow-only log to hunt through.
See [Sessions and runs](/docs/concepts/sessions-and-runs) for what a run
record holds and how long it stays around.
