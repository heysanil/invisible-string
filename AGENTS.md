# AGENTS.md — working in this repo

Operational contract for anyone (human or agent) changing this codebase. `CLAUDE.md` is a symlink to this file. Read this first; it tells you what is load-bearing, how to verify changes, and which documents are the source of truth.

**invisible-string** is a multi-tenant cloud platform for AI agents: users build **Agents** (PERSONA · MODEL · CONTEXT — MCP connections & skills) in a chat-centric SPA; each **published Agent compiles to a self-hosted [eve](https://eve.dev) agent** (`packages/compiler` → `eve build` → tarball in object storage) that runs on a stateless worker pool with Postgres-backed durability (`@workflow/world-postgres`). Users chat with Agents directly, or delegate standing work with **workflows** (TRIGGER → STEPS; webhook/form/Slack/schedule) — a workflow is a **pipeline the control plane interprets**: deterministic `tool` calls on workspace MCP connections, direct-model `infer` steps, real-eve `agent` steps run as child runs, and `for_each`/`branch`/`filter`/`state` control verbs. A workflow still builds nothing — agent steps ride the bound agent's compiled artifact. An AI copilot lives in both editors.

## Golden rules

1. **Commit messages never mention AI assistance** — no Claude references, no `Co-Authored-By` trailers. Conventional style: `feat(scope): …`, `fix: …`, `integrate: …`, `test(e2e): …`.
2. **Secrets never touch git, logs, or model context.** `.openrouter-key` (local provider key) and `.env` are gitignored — keep them that way. Secrets at rest use AES-256-GCM envelope encryption with AAD tenant binding (`packages/shared/src/crypto.ts`); API responses expose `hasCredentials` booleans, never values. The structured logger redacts known secret keys — use it, not `console.*`, in control-plane/worker hot paths.
3. **Migrations are additive.** New columns/tables/indexes via `bun run --cwd packages/db generate`; never edit an applied migration. Schema and Better Auth tables live only in `packages/db` (control-plane re-exports).
4. **Compiler changes have a versioning ritual.** Any edit that changes emitted bytes requires bumping `COMPILER_VERSION` (`packages/compiler/src/version.ts`) — the golden-digest guard (`fixtures/.golden-digest.json`) fails CI otherwise, and `UPDATE_GOLDEN=1` refuses to run without the bump. Build-environment changes that alter artifacts bump `BUILD_ENV_EPOCH` (`apps/control-plane/src/build/steps.ts`), which flows **through** `compile()` into the content hash (the platform-JWT audience bakes the hash — never re-key outside `compile()`). **`packages/compiler/versions.json` is hashed WHOLE — including its prose `notes` and `generatedAt`.** `RUNTIME_VERSIONS` is the entire parsed file (`packages/compiler/src/index.ts`) and `computeAgentHash` feeds it in as `versions: deps.versions`; the `RuntimeVersions` type narrows the STATIC view only, while `canonicalJson` walks the runtime keys. So adding one explanatory sentence to `notes` re-keys **every agent version** — new artifact, new world DB `ag_v_<hash12>`, new JWT audience, every published agent orphaned from its world and needing a republish. Rationale prose about the matrix belongs in this file or a doc, never in `versions.json`; edit that file only to change a pin you actually intend to ship. The golden-digest guard catches it, which is why the fixtures fail on what looks like a comment-only change.
5. **The E1 design system is law in `apps/web` and `apps/site`.** Monochrome ink × liquid glass: tokens in `packages/design-tokens/tokens.css` (consumed via `@invisible-string/design-tokens/tokens.css` by both apps), primitives in `src/components/ui` (or `apps/site`'s local equivalents) — extend them, never fork one-off styles. Color only as meaning (`#16a34a` success · `#f59e0b` waiting · `#dc2626` error). Capsule controls, 150–200 ms ease-out, `focus-visible` everywhere, designed empty/loading/error states, `prefers-reduced-motion`/`-transparency` respected. Full tokens: design spec §E1.
6. **TypeScript strict everywhere; contracts live in `packages/shared`** (zod schemas mirroring db enums). API DTOs, WS frames, TriggerEvent, eve event types — server and web both import from shared; never let them drift.
7. **Workspace scoping is mandatory on every route**: resolve the Better Auth session + active organization + role (`requireWorkspace`), verify row ownership (sessions/runs map to workspaces — eve does not enforce this), and test the authz matrix (outsider 403, member vs admin/owner ops).
8. **Verify before you claim done**: typecheck + the test lanes relevant to your change (below). If you touched runtime/worker/compiler paths, run the acceptance suites.

## Toolchain & setup

- **`mise.toml` at the repo root pins every host tool** — bun (runs the platform: control-plane, worker, web/site tooling, all tests), node (runs everything eve: `eve build` during a publish, and the compiled agent processes), and wrangler (the `apps/site` Cloudflare deploy). Setup is `mise trust && mise install`; CI does the same via `jdx/mise-action@v4`, which reads this file. Pins are EXACT, and `node` is DERIVED from `packages/compiler/versions.json` — bump both in the same commit (guard: `tests/integration/toolchain-pins.test.ts`, ungated).
- **Prefer config-driven mise invocations over fuzzy ones**: `mise install`, `mise where node`, `mise exec -- npm …` — never `node@24`. A fuzzy request resolves to the newest matching release, which may not be the pinned one, and would then win the "newest installed 24.x" race in `resolveNodeBinDir()`/`resolveNodeBin()` — silently bypassing the pin. In CI mise's shims are on `PATH`, so a bare `bun`/`node`/`npm`/`wrangler` in a workflow step is already the pinned version; no `mise exec` wrapper needed.
- At RUNTIME the apps never shell out to the mise binary: control-plane build steps and the worker both resolve a Node 24 binary directly (`BUILD_NODE_BIN`/`WORKER_NODE_BIN` override → newest mise install → PATH) — the prod images bake bare node + an `oven/bun` base and carry no mise (which is why the Dockerfiles' bun minor line is guarded against `mise.toml`). **Docker** for compose + `docker()` sandboxes.
- `bun install` once at the root (single lockfile). `cp .env.example .env` and fill secrets for running apps (tests provision their own env).
- Local stack: `docker compose up -d postgres garage dex meilisearch` (ports overridable: `POSTGRES_PORT`/`GARAGE_PORT`/`DEX_PORT`/`MEILISEARCH_PORT`). Test harnesses spin their own compose **projects** (`p1acceptance`, `p2e2e`, `p3acceptance`, `pkeyed`…) on non-default ports — don't reuse those names.
- Dev servers: `bun run dev` at the root does it all — bootstraps `.env` with generated secrets on first run, `docker compose up --wait`, migrations, then API (:3000) + worker + SPA (:5173) with prefixed logs; Ctrl-C stops the apps, `bun run dev:down` stops infra. Individual apps: `bun run --cwd apps/<x> dev`. Backend-free UI preview: `VITE_FIXTURE_MODE=1`. The marketing/docs site (`apps/site`) is standalone — it needs no infra and is not part of `bun run dev`; run it with `bun run --cwd apps/site dev`.

## Releases (changesets)

Every behavior-affecting PR adds a changeset — same commit as the change, the same way docs move with code. Write the file directly rather than running `bun changeset`; the prompt walks all ten workspaces:

```md
<!-- .changeset/any-name.md -->
---
"@invisible-string/web": minor
---

Replace the markdown renderer with Streamdown.
```

- **Bump types while on 0.x**: breaking → `minor` (semver §4 — anything may change below 1.0), feature → `minor`, fix/chore → `patch`. **`major` is reserved for the deliberate 1.0.0 cut** and is not used before then.
- **Mark breaking changes** by starting the summary with `**Breaking:**`. That marker, not the bump type, is what routes an entry to the changelog's "Breaking changes" section — necessary precisely because a 0.x breaking change ships as a `minor`.
- **The summary is ONE line.** `parseChangeset` collapses the whole body into a single space-joined line, so bullets, sub-lists, and fenced code inside a summary come back out as a run-on sentence. Write one sentence (a few clauses at most) on one logical line.
- **The bold scope label in `CHANGELOG.md` is DERIVED, not authored** — it is the changeset's package names with `@invisible-string/` stripped, **sorted alphabetically**, comma-joined. Naming `web` and `shared` renders `**shared, web**`, never `**web**`; which packages you name is the only lever you have over it.
- **Name only shipped workspaces.** `@invisible-string/e2e` and `@invisible-string/integration-tests` have no `version` and are excluded. Naming one alone makes changesets exit 0 and silently never consume the file — a zombie that blocks nothing and fixes nothing; naming one alongside a shipped package fails with "Mixed changesets that contain both ignored and not ignored packages are not allowed". `bun run release:version` rejects both up front with a file-and-package message, and `tests/integration/changesets-config.test.ts` guards the config that makes the exclusion work.
- **All eight shipped workspaces share one version** (`fixed` globs), because `docs/DEPLOY.md` pins all three images with a single `IMAGE_TAG`.
- **Never `git clean -fd .changeset`.** A changeset you just wrote is untracked until you stage it, so the sweep that clears build junk deletes precisely the file the PR exists to carry — and it does so in the exact state you are in right after writing one.
- **Never run `bun run release:version` locally — not even to "check" it.** It takes NO flags: `scripts/release-version.ts` parses no argv, so `--help`/`--dry-run`/`-n` are ignored and the real bump runs. It CONSUMES every pending changeset (changesets deletes the files), bumps all eight manifests, and writes `CHANGELOG.md` — destroying not just your own untracked changeset but every other PR's pending one still sitting in `.changeset/`. It exists to be called by the `release.yml` shell step and nowhere else. Recovery is `git checkout -- CHANGELOG.md .changeset/ <every manifest>`, which restores the TRACKED changesets but cannot bring back an untracked one you had just written — rewrite that by hand.

Releasing is merging: pushes to `main` keep a PR titled **`chore(release): version packages`** (branch `changeset-release/main`) up to date; merging it bumps the manifests, writes `CHANGELOG.md`, tags `vX.Y.Z`, cuts the GitHub Release, and builds the GHCR images — in one workflow run, so no PAT is needed. Search for that exact title; the PR is opened by a shell step in `release.yml`, **not** by `changesets/action`, which is unusable here for the two reasons that step documents (an unguarded per-package `CHANGELOG.md` read that `changelog: false` makes fatal, and a checkout it leaves on the version branch) — do not "simplify" the step back into the action. Pushing a `v*` tag by hand still builds images, but the manifests must already be aligned to that version **in the tagged commit** or the number is burned — `release:tag` reads the comparison version out of the tag's own commit, so an alignment commit landed afterwards cannot repair it (recovery: `docs/DEPLOY.md` §10).

Two repository facts the flow depends on — check both before blaming the workflow:

1. **"Allow GitHub Actions to create and approve pull requests" must be ON** (Settings → Actions → General). This is merge-blocking, not a nicety: with it off, `gh pr create` fails with a permissions error that never names the setting, so the `version` job fails on every push that leaves changesets pending — i.e. effectively every push between releases — and releases go permanently red.
2. **The version PR runs no CI checks** — a `GITHUB_TOKEN`-opened PR does not trigger `pull_request` workflows. Benign while `main` has no branch protection; add a required status check and the version PR becomes unmergeable until the step is given a PAT or GitHub App token.

## Architecture (one screen)

`apps/control-plane` (Bun+Elysia): Better Auth (email/pw + OIDC SSO + orgs; workspace creation seeds starter Agents and fire-and-forget-publishes "General Purpose") · agent + workflow CRUD · connections (rebuilt domain on the `connections` table, `cn_` nanoid ids; three create sources — curated catalog-as-code from `packages/shared/src/connector-catalog.json` validated at boot, registry installs re-verified against the live official registry, custom URLs) · connection health probes (`src/probe`: MCP initialize + `tools/list` via the official SDK client through the guarded egress fetch, classified `ok`/`unreachable`/`auth_required`/`auth_error` with the tools cache written only on `ok`; credentials come from the row's static auth envelope OR, for an `oauth` row, from `getAccessToken` — fire-and-forget after create for static auth only + `POST …/connections/:id/probe` test-connection routes — an unhealthy server is a 200 with its classification, 502 `probe_failed` means the probe infrastructure itself failed) · MCP OAuth broker (`src/oauth`: RFC 9728/8414 path-aware discovery, scheme/issuer/resource-validated → pre-registered client identity (operator config) → CIMD → DCR keyed by issuer → PKCE popup consent with persisted single-use state bound to the initiator, every hop through the guarded egress fetch; discovery and client identity stage on `connection_oauth.pending_flow` and are promoted onto the grant only by a successful exchange; tokens at rest as AES-256-GCM envelopes, refreshed centrally under a single-flight row lock where only `invalid_grant` is terminal; compiled agents fetch live access tokens from `POST /internal/connections/token`) · registry→Meilisearch sync ETL (advisory-locked ticker, `REGISTRY_SYNC_INTERVAL_MS`, default 6 h) mirroring the official MCP registry into the disposable `mcp_registry` index that backs `GET /mcp-registry/search` (typo-tolerant, verified-publisher-first; meili absent/down → typed 503 `search_unavailable`, catalog + custom lanes unaffected) · compiler invocation + `eve build` + tarball → object store (Garage) (cache keyed by content hash = agent definition + the resolved model **and reasoning effort** + compiler version + eve version + build-env epoch) · scheduler (session affinity → artifact-warm → any live worker; dead-worker sweep + fencing) · trigger ingress (`/t/:token`, Slack events with signature + replay window) + schedule ticker (advisory-locked cron claims, `SCHEDULE_TICK_MS`) + remote-cancel sweeper (`REMOTE_CANCEL_SWEEP_MS`: reconciliation's pending-remote-cancel sweep re-run periodically so a Stop's eve leg that was refused or failed in transport is finished without a restart) → **pipeline runner** (`src/pipeline`: every workflow dispatch path starts a `mode:'pipeline'` run — no eve session of its own — that the control plane INTERPRETS: sequential driver over the `run_steps` ledger claimed by `(run_id, path)`, per-run session-level advisory lock on its own bounded pool (`DB_PIPELINE_LOCK_POOL_SIZE`; exhaustion is the typed transient skip `lock_pool_exhausted`, nothing created), crash recovery by replay from the ledger — at boot AND on the periodic pipeline-recovery sweep (`PIPELINE_RECOVERY_SWEEP_MS`, default 60 s: adoption is lock-gated, so a run left `locked` at boot by an exhausted pool or a dead replica's driver is re-driven by a healthy process instead of holding its cap slot until a restart), `overlap:"skip"` by default, `pipeline.*` events appended beside eve events under one monotonic `seq`; `tool` steps call MCP through the probe's dial machinery + guarded egress, `infer` steps call a workspace preset through `model/reasoning.ts`, `agent` steps spawn CHILD runs via `dispatchRenderedRun` — worker-select → ensure-agent → eve session create/continue, ID-addressed, with a version-bound JWT, `mode:"task"` + declared `outputSchema` on fresh children; the `TriggerEvent` envelope is stored on the run as provenance only) · pipeline HTTP surface (`src/pipeline/routes.ts`: workflow run history, the `run_steps` ledger, workflow-state operator surgery, the per-step test route — all under the existing `/workspaces`/`/runs` prefixes) · outbound reply delivery (`DeliveryService`: EXPLICIT only — a slack-origin pipeline run declaring `onComplete.slackReply` renders it against the final run scope; at-least-once, with boot recovery re-rendering from the `run_steps` ledger) · NDJSON tailer → `run_events` → resumable SSE · chat-session titler (`src/resources/session-title.ts`: after a new chat session's first user message, a fire-and-forget round-trip on the platform key against the workspace's `quick` preset writes `agent_sessions.title`; ## Constraints that will bite you (learned empirically — full list in the design spec's "Live-doc corrections" + `spike/REPORT.md`)

- eve bakes **model routing at `eve build` time** — the build step injects a placeholder OpenRouter key so artifacts get external routing; never "clean up" that placeholder, and never let real keys into build env (allowlisted + `--ignore-scripts`).
- **Reasoning effort does NOT reach OpenRouter through eve's `reasoning:` config** — eve forwards it to ai@7 as a top-level call option and `@openrouter/ai-sdk-provider@3.0.0`'s `getArgs()` never destructures it, so it is silently dropped (spike finding 29). The codegen emits it as `openrouter(MODEL_ID, { extraBody: { reasoning: { effort } } })` — `extraBody` is spread last over the body — and a bare `openrouter(MODEL_ID)` for `provider-default`. Don't "simplify" it back onto the config route, and don't use the provider's typed `reasoning` setting either: its effort union has no `max`. Anthropic is the opposite — spec-v4, so it keeps `reasoning:` (with `max` clamped to `xhigh`). The effort is **resolved at publish** (agent override → preset's effort, or `provider-default` behind a modelId override) and hashed into the artifact: preset changes only land on the **next publish**. Both halves are proven, not inferred: the wire probe captures `reasoning:{effort}` in the compiled artifact's real request body, and against the live API `effort:"max"` on `moonshotai/kimi-k3` returns 5.8× the reasoning tokens of `"low"`, while a reasoning block sent to a model advertising none is silently IGNORED (200, zero reasoning tokens) — which is why `provider-default` is an offered value, not a forced resolution for effort-less models. **That `extraBody` rule now governs the CONTROL PLANE too.** `apps/control-plane` used to sit on `@openrouter/ai-sdk-provider@6.0.0-alpha.1` — a **stale parallel alpha** published 2026-01-07, six months BEFORE 3.0.0 became `latest`, which semver sorts ABOVE the stable line so "6 > 3" reads as newer forever. That line built a whitelisted Responses-API body and STORED `extraBody` WITHOUT READING IT, so neither route reached the wire and every titled session silently ran at the model's default effort. The pin is now aligned to `versions.json` (provider `3.0.0`, `ai` `7.0.58`, `@ai-sdk/anthropic` `4.0.36`) and the direct SDK callers route per provider through **`apps/control-plane/src/model/reasoning.ts`**: OpenRouter gets `openrouter(id, { extraBody: { reasoning: { effort } } })` (effort **verbatim** — only Anthropic clamps `max`→`xhigh`, because only its SDK union forces it), Anthropic keeps ai@7's top-level `reasoning` option. Bumping the pin alone would have fixed NOTHING: 3.0.0's `getArgs()` still never destructures `reasoning`, which `model/reasoning-wire.test.ts` asserts on real request bytes alongside both providers' positive routes (OpenRouter through the titler and the copilot; Anthropic through the helper, since neither caller takes an Anthropic base URL). The copilot's effort is deployment config (`COPILOT_REASONING_EFFORT`, default `provider-default` = no block, since reasoning bills to the platform key on every turn); the titler's comes from the workspace's `quick` preset. Drift guard: the control-plane pin block in `tests/integration/toolchain-pins.test.ts` (ungated) — the four shared AI SDK deps must equal `versions.json`, and none may carry a prerelease tag.
- **OpenRouter `-latest` alias ids carry a leading `~`** (`~deepseek/deepseek-v4-flash-latest`) — it is part of the id, not a typo. `modelIdShapeProblem` (`packages/shared/src/api.ts`) must keep allowing it or a seeded preset's model cannot be allowlisted at all.
- Proxies must forward **both** `/eve/` and `/.well-known/workflow/` or runs stall silently; world callbacks ride `/cb/<boot-token>/…` on the worker.
- **One world Postgres database per agent version** (`ag_v_<hash12>`); the graphile job prefix does NOT isolate. **Single writer per version hash** across workers — enforced by fencing + scheduler reservations; don't weaken either.
- **The content hash keys on the agent's stable id, and agent names are NOT unique.** Until the 2026-08-11 spec's D1 the hash carried only `agentSlug` (a slugified DISPLAY NAME), so two agents in one workspace with the same name and the same definition hashed identically and shared one `ag_v_<hash12>` — the single-writer violation above, held off only by a cosmetic unique index. `CompileDeps.agentId` (the `agents.id` uuid) is now a hash input, the unique index `agents_organization_id_name_uidx` is **dropped** (migration `0011`, replaced by a plain index), and duplicate names are legal end to end — nothing in the API or the SPA may reject or auto-rename one (`nextUntitledAgentName` is a readability nicety, not a constraint). Two consequences that bite: **(a)** anything inserting `agents` rows may NOT use `ON CONFLICT (organization_id, name)` — Postgres needs a unique constraint to infer an arbiter and now raises `42P10`, which took workspace creation itself down; `seedWorkspace` reads existing names under its advisory lock instead. **(b)** `agentSlug` still feeds the hash, because it still shapes emitted bytes (generated package name, the model-visible identity line) — so renaming an agent still re-keys its artifact, world DB, and JWT audience. That is known churn, deliberately out of scope, and NOT a reason to drop the slug from the hash.
- **An idle clear/compact has NO tail — the route must drain eve's frames itself.** `POST /sessions/:id/{clear,compact}` refuse a busy session, so by construction nothing is following the stream when they fire, and the thread's context divider is DERIVED from persisted `run_events`. Left unconsumed those frames do double damage: no divider is persisted (none survives a reload), and the session-wide event count IS the tailer's `startIndex`, so the NEXT run's tail drains them and draws the boundary under an exchange that happened AFTER the clear. The accepted path appends them to the session's latest run and answers `marker: {kind, runId} | null`; `null` is a real outcome (an empty or already-cleared context emits no `compaction.*` at all) and no surface may claim a boundary on it. The drain is bounded and best-effort — a bookkeeping miss must never fail a control that reached eve.
- **A preset is NOT identifiable by its model id.** `balanced` and `quick` seed to the SAME model id and differ only in reasoning effort (`packages/db/src/seed.ts` says so), so `presets.find(p => p.modelId === id)` returns whichever the API listed first and labels every Quick agent "Balanced". Read the preset from the definition that was compiled (`publishedDefinition.model.preset`, gated on the session still being pinned to the published version); a specific-model override or an older pinned version has no preset to name and must degrade to the model's friendly short name, never a raw slug.
- **Copilot `thought`/`step` keys must be unique for the whole SOCKET, not the turn.** The dock upserts timeline items by key GLOBALLY (`apps/web/src/lib/copilot/thread.ts`), so the obvious `step:<stepIndex>` collides on every turn after the first — each turn's step loop restarts at zero — and turn 2's reasoning silently overwrites turn 1's inside its old work block. The server mints `turn:<turnIndex>:step:<stepIndex>` off a never-reset per-session counter; the key is opaque to the client. Note also that agent identity (`name`/`description`) rides the `user_message` frame's own `identity` field and WINS over the persisted row — it is not part of `draft` and the server does not read it there.
- **Both streaming carets must contribute zero inline advance.** A caret with real inline width creates a line-break opportunity at the right edge and gets orphaned onto a line of its own mid-stream. `apps/site`'s `.stream-caret` (an atomic inline-block) cancels its advance with a negative end margin; `apps/web`'s Streamdown glyph is inline TEXT whose leading space is the break opportunity, so it needs a different mechanism (a zero-width box) — the two fixes look nothing alike on purpose. `white-space: nowrap` is NOT a substitute (the break belongs to the ancestor containing the text) and any surface rendering a caret needs ~20 px of end gutter, since the ink now paints into the padding. Guard: `tests/integration/e1-css-invariants.test.ts`, which also pins `.lift`'s hover swell (`scale(1.01)`, never `translateY`) and the `transform: none` reset in the unlayered `prefers-reduced-motion` block — the duration clamp beside it only makes the motion instant, it does not remove it.
- eve sessions are **ID-addressed** (session API v2, eve 0.31): create is 202 async, follow-ups POST to `/eve/v1/session/:id` with `message` **XOR** `inputResponses`, and every session route 400s if the body carries a `continuationToken` key at all (an `in`-check, so `{continuationToken: null}` fails too). Continuation tokens are gone; `session.waiting.data.continuationToken` is a compat echo of the session id — never read it back. Shapes + guards: `packages/shared/src/eve-session-api.ts`; routes: `docs/runtime-worker-contract.md`.
- **Two 409s, opposite recoveries — never collapse them.** `session_busy` is the PLATFORM's one-run-per-session guard (`waiting` counts as busy, and so does another dispatch holding the session's per-session dispatch lock — `runtime/session-lock.ts`, the advisory critical section every eve-ward dispatch holds across its eve call + settlement — never across a tail, a Stop's observation included; a saturated lock pool reads as busy too) — transient, retry. `session_not_active` is eve's — and the platform's own verdict when a continuation re-reads its session closed UNDER the lock, or a lock-holding dispatch heals an abandoned eveless session (`healAbandonedEvelessSession`: the lock proves no dispatch is in flight, so the row is closed inline instead of answering busy until a boot sweep; the chat route surfaces it as `session_not_continuable`) — and it is PERMANENT for that session id (unknown / terminal / reset / timed out): release the Slack thread claim and mint a fresh session; never retry. **The lock rides its OWN pool** (`Db.$lockClient`, `DB_LOCK_POOL_SIZE`, `src/db.ts`): a holder pins a connection for its whole eve round-trip while its queries keep drawing from the root pool, so locks on the root pool deadlock at `max` concurrent dispatches — never route them through `$client`, and never `acquire()` inside a transaction. **The pipeline runner's per-run driver lock is the other long-held family and rides a THIRD pool** (`Db.$pipelineLockClient`, `DB_PIPELINE_LOCK_POOL_SIZE`, default 32): a driver pins its connection for the run's whole wall clock, so on the root pool ten long pipelines wedged the entire control plane, and on the session lock pool a pipeline burst would starve every chat Stop — the pool bounds concurrent pipeline runs, its reserve is bounded, and exhaustion is the typed transient skip `lock_pool_exhausted` taken BEFORE the run row exists (a pre-minted run id, nothing created; 503 `pipeline_lock_pool_exhausted` on webhook/manual ingress, a logged drop on Slack/schedule, metric `is_pipeline_dispatches_total`), never a queue. **A fresh session's id is pre-minted** so its lock is taken BEFORE the claim transaction (a timeout creates nothing), and every session status write on the dispatch path is a CAS against a still-live row. **A remote cancel is CONFIRMED by eve's own stream, never inferred locally and never taken from a 202** — every local signal is forgeable (`runs.status = running` is synthesized when reconciliation re-tails an unsent continuation; `run_events` under a run can be a predecessor's leftovers; eve answers an unqualified pre-turn cancel with 202 while consuming it as a no-op), so the ONLY acceptance proof is `runs.turn_id`, written by the tail when it attributes the run's own turn — **by CONTENT, never by send order**: eve's 202 carries no turn id, but every content turn opens with `turn.started` + `message.received {message: <the exact text sent>}`, so the dispatch-attempt CAS records `runs.message_hash` (sha256 of the exact message — the digest only, never the text) beside the marker, and the tail holds a `turn.started` until the next event and matches its `message.received` against the session's open obligations (pending before unresolved, oldest first), then its own run, then a live successor — anything else is a FOREIGN turn (persisted, never attributed, never cancelled). **Those obligations are CURRENT, not a start-of-tail snapshot**: the tail re-reads them from the store at every turn opening, every boundary, its own settlement and on the manager's signal (`refreshSessionObligations`, sent by the guarded settlement / a refused `observe()`), because a continuation Stopped before its own tail started settles with NO tail and lands on the live reader — whose stale list would persist that run's turn as foreign (terminal, so the live-successor lookup missed it too) and let the Stop age out unresolved. The claimants are ONE store read (`RunStore.listSessionClaimants`: obligations + live unattributed runs in a single statement — two reads left a no-tail Stop committing between them in NEITHER result, its open turn foreign), and adoption is RETROACTIVE (`listUnownedContentTurns`: an obligation adopted with a null turn id is matched against the session's persisted unowned content turns, so it never waits for an opening that already went by). And the handoff to a live tail checks LIVENESS: a tail leaves the manager's reader slot synchronously when it CLOSES — `close` is the one exit transition, taken at the start of every path out (an abort, the natural terminal, reconnect exhaustion; never at `done.finally`, which can trail a hung reconnect) — `refreshSessionObligations` answers false for a closed tail, and every caller then opens its own observer — chained behind the draining tail's cursor (`isSessionStreamHeld`), one reader per stream; that chain wait is bounded (`streamTakeoverMs`, 5 s: a hung drain is seized and fenced, its cursor taken over) and a chained observer's `REMOTE_CANCEL_OBSERVE_MS` deadline is armed at creation, so a drain that never releases can wedge neither the observer nor the session. And attribution, settlement and that refresh run on ONE per-tail serial queue (`runs/tailer.ts`): a Stop / the wall-clock cap / shutdown never snapshots `ownTurnId` while an attribution's `setRunTurnId` is in flight — it settles after the attribution, re-reads `turn_id` after finalizing, and sends the qualified cancel at once if the id is known. A HITL `inputResponses` resume opens with NO `message.received` (content-less; its sender's hash is null), so such turns are attributed among content-less senders only, in send order — `runs/tailer.ts`. `runs.remote_cancel_pending_at` is set in the same CAS that settles a Stop `canceled` on every path (the live tail's finalize included, never a second statement after it) — and that settles the wall-clock cap / shutdown `failed`: the tail sends a turn-QUALIFIED cancel if it knows the turn and NOTHING if not (never an unqualified cancel, for any cause), then stays on the stream in OBSERVATION mode; the obligation clears only on the run's own turn boundary after its own turn was attributed, a session-terminal answer from eve (`session_not_active`/`no_active_turn`/`session.failed`, and a `reset` — the retired id settles every obligation on the row), a NEWER run whose `turn_id` is set (`classifySessionSuccessor` — nothing else counts), or evidence already on disk (never sent; own boundary persisted; eveless session closed). Past `REMOTE_CANCEL_OBSERVE_MS` (default 10 min) it is declared UNRESOLVED on the row (`remote_cancel_unresolved_at`, marker kept, warn) — never silently cleared, and still attributable: a late content match clears both columns. One reader per eve stream: a successor's normal tail takes the session's obligations over from a detached observer through its leftover drain, and clear/compact/reset answer `session_busy` while an observation tail is on the session (their drain must never be a second reader) — and they HOLD the session dispatch lock from that quiet check through the eve call and the drain/settlement (`withQuietSessionControl`, bounded try → `session_busy`), because the check alone is a read: without the lock a follow-up could be admitted and sent between "quiet" and the drain attaching (two readers, duplicate `(run_id, seq)`), and a reset could retire a session under a dispatch it had just admitted; the no-tail settlement (`settleRemoteCancelGuarded`, under the lock), the periodic sweep (`createRemoteCancelSweeper`, `REMOTE_CANCEL_SWEEP_MS`) and boot reconciliation re-open observation (`startObservation`) instead of chasing eve with an unqualified cancel — the post-eve recheck too. eve's truth can lag `agent_sessions.status` indefinitely, so this 409 is the second thread-key release trigger. Likewise `no_active_turn`/`no_active_session` (200 on the control routes) mean the SAME dead-session condition — not "nothing was running". The workflow-side consumer of this doctrine is now the **`agent` step executor** (`pipeline/steps/agent.ts`): its only retryable failures are dispatch-phase — `session_busy` retries; `session_not_active` evicts the dead thread claim so the retry mints a fresh session; a failed child TURN is never retried.
- Turn cancellation is real (`POST /eve/v1/session/:id/cancel`) and is **a user decision, never an error**: the stream settles `turn.cancelled` → `session.waiting`, the run lands `canceled` (never `failed`, and never `succeeded` — an unhandled `session.waiting` would classify it succeeded and post a truncated Slack reply). Cancellation is cooperative at durable step boundaries: an in-flight tool call still completes.

A pipeline has no well-defined "final assistant message", so nothing is guessed; agent-step CHILD runs never owe a reply. `SLACK_BOT_TOKEN` must never enter agent env or generated code; agent env is identical across all dispatch paths.

Every `runs ⋈ agent_sessions` read must therefore be a LEFT join resolving the org as `COALESCE(runs.organization_id, agent_sessions.organization_id)` — an inner join silently drops pipeline runs, which on `countActiveRuns` is a workspace-cap bypass (a dedicated caps test asserts pipeline runs hold slots). Parent and agent-step child runs EACH hold a cap slot.

- **Every caller-influenced outbound fetch from the control plane goes through `createGuardedFetch`** (`apps/control-plane/src/net/guarded-fetch.ts`): DNS-resolve and validate EVERY address, then dial with the socket pinned to a validated IP while TLS still verifies the real hostname — re-dialing by hostname after validation would be a DNS-rebinding TOCTOU; redirects are same-origin only with the full guard re-run per hop; HTTPS-only; timeout + response-size caps. Consumers today: the MCP probe and the entire OAuth broker — discovery, DCR, token exchange, refresh, revocation (a malicious MCP server chooses its own authorization server). Exempt by design: the registry proxy (one hardcoded host) and the Meilisearch client (operator-configured host). `MCP_PROBE_ALLOW_PRIVATE=1` relaxes BOTH the private-range rejection and HTTPS-only — dev/e2e/self-hosted only, never production. Credentials decrypted for a probe live in function scope only (never logged, never persisted, never in a DTO), and probe `last_error` strings are scrubbed against every header value before persistence. **The guard is not the only lock on a server-supplied URL, because not every use of one is a fetch**: the SPA NAVIGATES an `about:blank` popup it opened to the authorization endpoint, a window that inherits the app's origin, so a custom MCP server advertising `javascript:` there would be script execution no egress guard ever sees. Every URL discovery accepts from a server — the `resource_metadata` pointer, the PRM's `resource` and `authorization_servers[0]`, and the AS's authorization/token/registration/revocation endpoints — is parsed and required to be `https:` (no embedded credentials, no fragment) at discovery time, and `apps/web`'s `isSafeAuthorizeUrl` refuses again before `popup.location.replace`. Neither check substitutes for the other, and `z.url()` is no check at all — it accepts `javascript:` and `data:` happily. `http:` is admitted only for the MCP URL's own scheme (dev stacks under `MCP_PROBE_ALLOW_PRIVATE`) and, in the browser, only on loopback.
- **An OAuth connection's credential is NOT where the probe looks for a static one, and `hasCredentials` is not a property of the auth TYPE.** Static auth (`bearer`/`headers`) is an envelope on `connections.auth_config_encrypted`; a grant's access token is an envelope on `connection_oauth.access_token_encrypted` and is readable ONLY through `getAccessToken` (`oauth/tokens.ts`), which is also where the central refresh happens. `decryptConnectionAuthHeaders` deliberately returns `{}` for an oauth row, so the probe built on it alone dialled with NO `Authorization` header, collected the server's entirely correct 401 and — because `hasCredentials` was hardcoded `true` for `authType === "oauth"` — persisted `auth_error`: "your token was rejected", about a token never sent. Every OAuth connection read 401 forever and none ever populated `tools_cache`, so none could fill the tool picker, the per-tool approvals, the version tool directory or the copilot inventory. `probe/service.ts` now branches: not oauth → static headers; oauth with no live grant → `auth_required` **with no dial at all**; oauth `connected` → `Authorization: Bearer` from `getAccessToken` (a 401 there is the only real `auth_error`). `oauth_not_connected` from that call is `auth_required`, `oauth_exchange_failed` is `unreachable` (the AS, not the MCP server, was unreachable), anything else is genuine infrastructure failure and rethrows as 502 `probe_failed`. Derive `hasCredentials` from the GRANT in both homes (`probe/service.ts` and `resources/common.ts` `connectionDto`) — a `pending` grant is not credentialed. And **an oauth row is never probed at create**: consent has not happened, so the only thing a dial could report is the absence of a grant, which the insert already states as `auth_required` — and once the post-callback probe carries a token, a create-time probe racing it can land LAST and overwrite a healthy result with that 401 forever. Not dialling removes the race by construction; a probe-generation counter would only narrow it. Same rule in the SPA: `ConnectionDetail`'s 15-minute stale re-probe skips a grant-less oauth row (`isProbeable`). And the same table in the pipeline **`tool` step** (`pipeline/steps/tool.ts`): grant status first — `pending`/absent fails `auth_required` with no dial; `getAccessToken`'s `oauth_not_connected` past `pending` is a non-retryable `auth_error`; `oauth_exchange_failed` is a RETRYABLE `unreachable` (the grant stays `connected`, the refresh token unspent — a 30-second AS outage must not fail a workflow permanently); `hasCredentials` on the call is what was actually presented. Its re-probe passes the executor's `oauthTokens` as `ProbePersistDeps.oauthBroker` — the probe cannot classify an oauth row without one.
- **The consent popup's `postMessage` target is the SPA's origin, not the API's** — `PUBLIC_WEB_URL` (`runtime/config.ts` `publicWebUrlFromEnv`, defaulting to `PUBLIC_APP_URL`), never `publicAppUrl`, which is the CONTROL-PLANE origin the callback and the CIMD document are served from. They coincide behind the production gateway and differ in every local dev stack (API :3000, Vite :5173); a `targetOrigin` that does not match the receiving window is dropped by the browser with no error, no exception and no devtools warning, so the SPA falls back to close-polling and reports a **dismissal for a consent that succeeded**. The payload is `{type, ok, connectionId, reason}` — `reason` a sanitized CODE the SPA renders through `OAUTH_FAILURE_COPY`, never a provider message, and never an OAuth value. Two more rules that go with it: a failed or abandoned re-consent must NOT wipe a working grant (`status: "error"` only when there was no usable grant to lose — otherwise a closed popup bricks a connection whose tokens are still valid, because `getAccessToken` gates on `connected`), and in the refresh path **only `invalid_grant` is terminal** — an AS 5xx, a timeout or a guard refusal never spent the refresh token, so nothing is persisted and the next demand retries. Writing a status there makes a 30-second AS outage indistinguishable from a dead grant and forces a needless re-consent.
- **A catalog OAuth preset declares HOW the broker gets its client identity, and "it has a registration endpoint" is not evidence it works.** `auth: {type:"oauth"}` means `dynamic` (CIMD when the AS advertises `client_id_metadata_document_supported`, else RFC 7591 DCR — which of the two is a runtime fact about the AS, which is why the catalog's two values collapse the DB's three). `clientIdentity: "preregistered"` + `clientEnvPrefix` means the AS gates registration behind an approved-client allowlist and the credentials come from operator config (`MCP_OAUTH_<PREFIX>_CLIENT_ID`/`_CLIENT_SECRET`/`_ISSUER`, parsed at boot — a half-configured provider or an unrecognised `MCP_OAUTH_*` suffix fails boot rather than surfacing as a 502 mid-consent). **`_ISSUER` is REQUIRED and exact-matched**, and `findOauthClientRegistration` fails CLOSED on a miss: an unpinned registration would match whatever issuer discovery reported, so a repointed MCP server could nominate its own AS and be handed your approved `client_id` and secret. "Issuer unknown on either side" is not evidence the two agree. This exists because **Vercel** shipped as a bare oauth preset and could never work: its AS omits CIMD, so the broker fell through to DCR and `https://api.vercel.com/login/oauth/register` answered `400 invalid_redirect_uri` to every unapproved client — a 502 behind an already-open popup, and no tuning of the DCR body can pass it. The entry is REMOVED; its host is pinned in `connector-catalog.test.ts`'s `REGISTRATION_GATED_HOSTS`, so re-adding it as `dynamic` fails the default lane, and re-adding it at all needs approved credentials plus a solution for its `response_modes_supported: ["web_message.opener"]` (this broker's callback is a redirect carrying `?code=`). Verify a new oauth preset with the gated `CATALOG_PREFLIGHT=1` lane, which walks it live — a shape assertion is exactly what let Vercel through.
- **An OAuth consent flow's discovered endpoints and client identity are FLOW state, and `startOauth` may not write one grant column.** The MCP server names its own authorization server, so everything discovery returns (`token_endpoint`, `revocation_endpoint`, `resource`, the DCR `client_id`/`client_secret`) is chosen by the party an AS mix-up controls — while `connection_oauth.token_endpoint` is exactly where `oauth/tokens.ts` replays a still-valid refresh token, with the client secret, months later and with no issuer check of any kind. Writing discovery onto the row at start time therefore turned every re-consent that did NOT complete — a closed popup, a declined consent, the broker's own RFC 9207 `iss` rejection — into delivery of the previous AS's refresh token to whatever endpoint the server had just advertised, and the F5 rule that deliberately keeps such a grant `connected` is what makes `getAccessToken` willing to send it. A start now writes ONE staged `connection_oauth.pending_flow` object (`PendingOauthFlow`, `packages/db`), the exchange reads its material from there, and a SUCCESSFUL exchange promotes it onto the grant in the same write that stores the tokens — so the endpoints a grant is replayed against are always the ones its own tokens were minted through. Never restore a start-time write of any of those columns, and never mix a staged `client_id` with a live `client_secret_encrypted` (two registrations; and under CIMD a null `clientId` MEANS the hosted metadata URL). The cost, deliberately accepted: two abandoned FIRST attempts register two dynamic clients, because nothing persisted the first. Guards: broker.test.ts's "a re-consent that never completes cannot repoint a live grant" (asserts the OTHER stub AS receives zero token requests when the refresh fires) and its succeeding twin.
- **`POST /internal/connections/token` shares the `/internal/*` prefix with the worker plane but NOT its auth model** — it authenticates a version-bound platform JWT the compiled agent self-mints (`runtime/routes.ts` `serveConnectionToken`; never `x-worker-secret`), and the version hash comes ONLY from the verified JWT audience, never from the request body. Agents reach it at `PLATFORM_API_URL` (the control-plane base URL as seen from the worker network, injected into agent env when configured; absent, oauth connections' tool calls fail with a missing-env error and nothing else breaks — never make it boot-fatal). The response is `{token, expiresAt}` only: refresh tokens and client secrets never leave the control plane, and no OAuth value (`access_token`, `refresh_token`, `client_secret`, `code`, `code_verifier`) may ever appear in a log line, error string, DTO, or agent env. A dead grant answers 409 `oauth_not_connected` — re-consent is the only recovery; the compiled agent surfaces it as a failed tool call, never a hang.
- **A provider's `error` string is a CLOSED VOCABULARY, never text.** Every OAuth hop that reads one — refresh, code exchange, dynamic registration — sends a credential on the way IN (the refresh token, the authorization code, the client secret), so a hostile or repointed authorization server can answer with the secret it just received. That string is not cosmetic: `probe/service.ts` classifies `oauth_exchange_failed` as safe detail and persists it to `connections.last_error`, which `connectionDto` returns to every workspace reader, and the agent-facing token route serializes the same message. Everything provider-authored therefore goes through `providerErrorCode`/`describeProviderFailure` (`oauth/error-codes.ts`), which allowlists the RFC 6749/7591/8628 codes and drops anything else to a bare `HTTP <status>`. **A character class is NOT a substitute**: `[a-zA-Z0-9_-]` — the obvious "machine code" shape, and what the older `sanitizeOauthErrorCode` used — is exactly the base64url alphabet, so any opaque token short enough to fit the length cap passes it unchanged. Only a closed set works, because no value can be both a credential and a member of it. Guard: `oauth/error-codes.test.ts`, which feeds it real credential shapes.
- **Bun's default `idleTimeout` (~10 s of socket inactivity on Bun 1.3.x) must stay disabled on both servers** (`BUN_SERVE_OPTIONS` in `apps/control-plane/src/index.ts`, `idleTimeout: 0` in `apps/worker/src/server.ts`; guard: `index.test.ts`). The default kills quiet SSE run tails mid-response (heartbeats default to 15 s — `SSE_HEARTBEAT_MS`) and cuts chat dispatches awaiting a cold agent boot before headers are written, surfacing as instant gateway 502s in prod. Any new Bun server that streams or awaits >10 s needs the same treatment.
- **Adding a workspace requires adding its `package.json` COPY to every `infra/docker/*.Dockerfile`** — `bun.lock` covers all workspaces, so a missing manifest fails the in-image `bun install --frozen-lockfile` even when the image never builds that workspace (guard: `tests/integration/dockerfile-workspace-manifests.test.ts`).
- **A server-only module added to the `packages/shared` barrel takes the whole SPA down.** The barrel `export *`s every sibling, so importing one DTO pulls in every module that does `import … from "node:crypto"`; Vite externalizes `node:*` and its shim throws on property ACCESS, killing the app at load with an error naming the Node builtin rather than the import that dragged it in. Each such module needs an entry in `apps/web/src/lib/server-only-shared-modules.ts` plus a stub beside it that mirrors its **runtime** exports (`export *` resolves against the stub, so a missing value is an undefined import). This is not hypothetical: `worker-token-crypto.ts` joined the barrel after `crypto.ts` was stubbed and broke `VITE_FIXTURE_MODE=1` entirely. Guard: `apps/web/src/__tests__/server-only-shared-stubs.test.ts`.
- **Never change a Tiptap editor's `placeholder` or `ariaLabel` after mount — it DESTROYS the user's draft.** Both are in `useEditor`'s dependency array (`apps/web/src/components/editor/RichTextEditor.tsx`), so changing either string tears the instance down and rebuilds it empty. This looks like the obvious way to express state ("Queue a follow-up…" while a run works) and silently eats whatever the user was mid-sentence on. State rides the submit BUTTON's accessible name and a separate hint paragraph instead — which is also why the copilot dock renders "Connecting…" as its own `<p>`. Guard: the placeholder-stability case in `apps/web/src/__tests__/chat-composer.test.tsx`.
- **A `focus()` that races editor creation must be QUEUED, never dropped.** `useEditor` does not always return an instance on first render: `@tiptap/react` latches `isSSR` at module scope, and when true it forces `immediatelyRender: false` and creates the editor in a later effect (`<StrictMode>`'s destroy→recreate leaves the same hole). `RichTextEditor` parks the request in `pendingFocusRef` and replays it in an effect keyed on `editor`; the old bare `if (!isLive(editor)) return` made focus vanish with no error. In tests that latch is decided by **filesystem iteration order** — whichever module first evaluates `@tiptap/react` decides for the whole process — which is why it reproduced on CI's ext4 and never on APFS. `ensureDomForThisFile()` (`apps/web/src/test/setup.ts`) now imports `@tiptap/react` inside its `beforeAll` to pin the latch to the browser value; don't remove that import.
- **`apps/web` markdown is Streamdown, and its Tailwind wiring fails SILENTLY.** `index.css` must `@source` `streamdown/dist/*.js` or Tailwind emits none of its utilities — prose renders unstyled and the streaming caret never appears, with no error anywhere. The path is relative to `apps/web/src/index.css` and bun does NOT hoist streamdown to the root `node_modules`, so the depth is `../node_modules/…`. Guard: `apps/web/src/__tests__/streamdown-wiring.test.ts`.
- **The seven shadcn→E1 aliases in `apps/web`'s `@theme inline` are load-bearing.** `--color-foreground`/`--color-muted*`/`--color-background`/`--color-border`/`--color-primary*` bridge streamdown's dist (written against shadcn tokens) onto the ink scale; nothing in this repo references them by name, so they look unused — deleting them silently flattens every border and muted label in a chat reply. Same guard.
- **Streamdown's `shikiTheme` prop is only a FALLBACK.** It resolves the theme as `plugins.code.getThemes() ?? shikiTheme`, so the stock `code` export of `@streamdown/code` (shiki's `github-light`/`github-dark`) silently wins and paints code blocks in a full-saturation palette E1 does not sanction — the prop then lies about what ships. Carry the themes on the plugin (`createCodePlugin({ themes })` in `apps/web/src/components/chat/Markdown.tsx`), at module scope like every other non-scalar streamdown prop. Guard: the min-theme assertion in `apps/web/src/__tests__/markdown-render.test.tsx`.
- **`apps/web` never reads identity through a Better Auth React hook.** `useSession`/`useActiveOrganization`/`useListOrganizations` are nanostores atoms with three separate traps: the session atom reports `isPending: false` while holding a snapshot it never refetched (so a render-time gate bounces a just-signed-in user straight back to `/login` — the double-login bug), the plugin atoms built on `useAuthQuery` fetch exactly ONCE per page load and permanently unbind their signal subscriptions on first unmount, and **no signal fires on `/sign-in/email` or `/sign-up/email`** — so `listOrganizations`/`activeOrganization` resolved while signed out stay 401 for the life of the tab, which is why chat rendered empty until a reload. Identity is the `viewer` query (`apps/web/src/lib/auth/viewer.ts`), fetched through the plain proxy calls (`authClient.getSession()`, `authClient.organization.list()`) that carry no cache; the auth decision for a NAVIGATION happens in `routes/_app.tsx`'s `beforeLoad` and never in a render that could read a half-resolved snapshot, and `fetchQuery` is required there because `ensureQueryData` returns stale data without revalidating. `AppLayout` deliberately keeps a live render-time observer beside the gate and it is not a relapse: `beforeLoad` runs only on navigation, and a session can end without one (revoked in another tab, expired on the wire), so something has to branch on the viewer between navigations. What made the old gate unsafe was the VALUE it read, not the fact that it read one in render — a Better Auth atom reporting `isPending: false` over data it never fetched. The observer reads authoritative query state with an honest `isPending`, and it branches on all three arms in the gate's own order: `error` (undetermined → retry card) before `null` (signed out → `/login`) before a `Viewer`. Ignoring `error` there is the specific bug that made the contract hold only on initial navigation. A cached `null` viewer counts as FRESH data too — TanStack Query treats only `undefined` as absent — so `staleTime` alone never re-reads a session after sign-in; every sign-in/sign-up/invite-acceptance path must clear or refetch the viewer cache (`completeSignIn`, `refetchViewer`) before navigating, or the gate happily hands back the pre-login `null` it already had cached. **The cache purge is keyed on the RESOLVED principal, not on the sign-in call**, and it runs inside the viewer query function: `completeSignIn`/`completeSignOut` only cover a switch made in the same tab, but cookies are shared across tabs while QueryClients are not, so a sign-out + sign-in elsewhere merely makes this tab's viewer refetch as somebody else — and `lib/queries/keys.ts` scopes user-level data under a bare `["me"]` prefix that is byte-identical for every user, so a mounted personal-skill or personal-connection route renders the previous account's rows under the new identity. Purging in the query function puts it strictly before the new value is committed; an effect afterwards is too late by construction. A THROW is not a principal change and must evict nothing. **And the viewer's focus/reconnect refetch must be `"always"`, never `true`**: `shouldFetchOn` in query-core 5.101.2 is `value === "always" || (value !== false && isStale(...))`, so `true` refetches only a STALE query — and this one is deliberately fresh for 30 s, which means a session revoked seconds ago survives the very refocus meant to notice it, and staleness alone never schedules a request. **Every auth call the gate awaits is bounded** (`AUTH_REQUEST_TIMEOUT_MS`, carried as an `AbortSignal` on `fetchOptions`, which Better Auth's dynamic path proxy forwards to `@better-fetch/fetch`): a proxy that accepts `/get-session` and never answers would otherwise leave `beforeLoad` pending forever with the retry card unreachable, because nothing throws. An abort rejects (better-fetch does not catch its own `await fetch`), which lands on undetermined — never on signed out. Recovery UI carries the mirror-image trap: `queryClient.removeQueries()` does NOT notify an already-mounted observer — `Query.destroy()` never dispatches — so a "clear the error and retry" control wired to `removeQueries()` alone leaves the same stale error on screen, and worse, it DETACHES the observer from the cache entry so a later fetch under the same key cannot reach it either. It needs a real fetch a mounted observer is told about (`refetchViewer`). `router.invalidate()` is not a substitute and not redundant either — the two recover different things, which is why `SessionUnavailableScreen`'s retry does both: `invalidate()` is the only thing that resets an ERRORED route match (the `errorComponent` path); when the match is instead `status: 'success'` and the error lives purely in query state (the `AppLayout` path), `invalidate()` alone may issue no fetch at all — `beforeLoad`'s `fetchQuery` sees the data still fresh under the 30 s `staleTime` (`isStaleByTime` reads `dataUpdatedAt`, the last SUCCESS, not the failed refetch) — so it is `refetchViewer` that actually reaches the live observer there. Better Auth still owns every mutation. Guards: `apps/web/src/__tests__/auth-client-surface.test.ts` (no hook re-exports, and no reach through `authClient.useSession()` — the dynamic path proxy resolves it at runtime with no import to catch), `auth-flow.test.tsx` (sign in once after a signed-out boot), `viewer-principal.test.tsx` (the external principal switch, asserted per rendered frame), `viewer-focus.test.tsx` (focus/reconnect liveness), and `auth-gate.test.tsx` (the gate — not the render observer — is what redirects, and activation is awaited).

## CI (`.github/workflows/ci.yml`)

`unit` (typecheck + `bun test` + web build + site build) · `integration` (compose + gated lane incl. spike) · `acceptance` (phase-1, real eve build) · `phase3-acceptance` (multi-worker) · `e2e` (Playwright) · `prod-compose` (compose lint/drift + the prod-compose publish smoke: real images built from the tree, `eve build` runs inside the control-plane container). Keyed lanes are deliberately **not** in CI.

**Every job installs its host toolchain the same way: `- uses: jdx/mise-action@v4`, with no `with:` block** — the action reads the repo-root `mise.toml`, sets `MISE_TRUSTED_CONFIG_PATHS` + `MISE_YES`, and puts mise's shims on `PATH`, so the bare `bun`/`node`/`npm`/`wrangler` calls in later steps are the pinned versions. Do NOT add `oven-sh/setup-bun`, `actions/setup-node`, or `install_args:`/`tool_versions:` — a second toolchain or a fuzzy version defeats the pin, and `tests/integration/toolchain-pins.test.ts` fails the unit lane if one reappears. mise-action hashes `mise.toml` into its own cache key, so a version bump self-invalidates; **v4 also scopes that key by runner image**, which this repo needs — `ci.yml` runs on Namespace and `site.yml` on GitHub-hosted `ubuntu-latest`, same OS/arch, and pre-v4.1 those two could restore each other's `~/.local/share/mise/installs/*` (surfacing as `does not have an executable named …` or SIGILL against a foreign glibc). Stay on the floating `@v4` tag rather than pinning a patch; v4's own major bump was the Actions Node 20 → 24 runtime deadline, nothing config-facing.

All jobs run on Namespace runners (`nscloud-ubuntu-24.04-amd64-*` labels). The eve npm cache (`~/.npm`) and Playwright browsers persist on a shared Namespace cache volume (tag `eve-npm`, mounted via `nscloud-cache-action` — no `actions/cache` tarball round-trips), and `release.yml` image builds use Namespace's pre-configured remote builders (no `setup-buildx-action`, no gha layer cache — cache lives builder-side). `release.yml`'s `version` job DOES need mise (it runs `bun`); its `images` job and all of `docs-sentinel.yml` do not, since neither runs a host toolchain binary.

`.github/workflows/site.yml` is a separate, deliberately non-Namespace workflow (`ubuntu-latest`): pushes to `main` touching `apps/site/**` or `packages/design-tokens/**` build the prerendered site (`VITE_SITE_URL=https://invisiblestring.io` at workflow level, plus **`SITE_INDEXABLE=1` on the deploy job and nowhere else**) and deploy it to Cloudflare Workers (assets-only Worker `invisible-string-site`, config in `apps/site/wrangler.jsonc`, `html_handling: "drop-trailing-slash"` + `not_found_handling: "404-page"` — real files serve 200 at the **no**-trailing-slash form the site's own canonicals advertise (the default `auto-trailing-slash` would 307 every one of them), everything else gets the NEAREST `404.html` at a genuine 404, which is why the build emits two of them: `dist/docs/404.html` renders the docs shell that the client router renders under `/docs/*`, `dist/404.html` the root not-found — serving one for the other is a hydration mismatch React rejects outright; `public/_redirects` 301s both `/docs` and `/docs/` to the overview) via the wrangler mise pins (`npm:wrangler` in `mise.toml`, installed under mise's own data dir — not `cloudflare/wrangler-action`, whose npm fallback installs in-project and can't parse Bun's `workspace:*` protocol); pull requests touching the same paths upload a preview version (`wrangler versions upload --preview-alias <branch>`) and comment the preview URLs on the PR (fork PRs skip — no secrets); the preview job deliberately does NOT set `SITE_INDEXABLE`, so preview versions ship `noindex,nofollow` on every page and `Disallow: /` in `robots.txt` and cannot compete with production in search. Secrets: `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID`. A static marketing/docs build needs no Namespace cache, and this keeps public-site deploys decoupled from the platform's CI runners.

**Claude reviews** are two more out-of-`ci.yml` workflows, both advisory — they post comments and must never gate a merge. `claude-code-review.yml` reviews every non-draft PR automatically; `claude.yml` runs only when a human writes `@claude` in an issue, PR comment, review comment, or review body. Both authenticate with **`CLAUDE_CODE_OAUTH_TOKEN`** (subscription billing — deliberately NOT paired with an `anthropic_api_key`, since a second credential alongside it causes spurious model-not-found errors); the secret is laundered through a job-level `OAUTH_SET` env so the step **self-skips rather than fails** where it is absent (forks, and any clone that has not set it). Model and effort come from the optional repo variables `CLAUDE_MODEL` / `CLAUDE_EFFORT`, defaulting to `claude-sonnet-5` at `xhigh`. Both post through the action's own GitHub App token, so the jobs hold only *read* scopes plus `id-token: write`.

Both jobs run with the same real toolchain, not just repo-reading tools: `fetch-depth: 0` (full history — the git commands below are useless on the shallow clone tag mode alone would need), mise + `bun install --frozen-lockfile`, and `docker compose up -d --wait postgres garage dex` (`TEST_DATABASE_URL` set at *step* level to the same fixed dev connection string `ci.yml`'s `integration` job uses, so `apps`/`packages`' DB-gated tests actually run instead of skipping). The `--allowedTools` grant covers every `bun`/`bunx`/`node`/`npm`/`npx` invocation, `jq`/`rg`, read-only git (`diff`/`log`/`show`/`status`/`ls-files`/`blame`/`rev-parse`/`merge-base`/`grep`), `docker`/`docker compose`, and the prod-compose drift script — everything a reviewer needs to actually typecheck, test, and inspect history rather than guess from the diff alone. Deliberately withheld: Write/Edit as explicit grants (tag mode's `acceptEdits` permission mode already covers file edits inside `$GITHUB_WORKSPACE`; granting them here would additionally permit edits *outside* it, per the action's own tag-mode source comment) and anything that pushes or opens PRs (both jobs hold read-only GitHub permissions — see below). Nothing stops `bun run dev` specifically; `Bash(bun:*)` is a prefix match, so the only guardrail against it or any other long-runner is the shared 30-minute `timeout-minutes` ceiling.

Six traps, all load-bearing. **(1) `track_progress: true` is what makes the reviewer able to act at all** — it forces the action into tag mode, which supplies `--permission-mode acceptEdits`, the tag-mode tool grants, and the GitHub comment MCP server. Agent mode (a bare `prompt:` without it) *parses* `--allowedTools` and grants nothing, so the run is denied on its first tool call, exits in ~15 s having posted nothing, and still reports success — a silent no-op that looks green forever. **(2) Neither job may use willow's `namespace-profile-claudes`**: Namespace profiles are workspace-scoped and none is defined for this account, and a `runs-on` label no runner matches does not fail — it queues indefinitely. Both use the same shape label as `unit`. **(3) `claude_args`'s `--allowedTools` MERGES with tag mode's own, it does not replace it** — the action's own docs state the base GitHub tools are always included, and willow's production behavior confirms it (its tracking comment still posts, which needs a tag-mode-granted MCP tool, despite `claude_args` also setting `--allowedTools`). **(4) The env-prefix trap**: Claude Code's Bash permission rules are a literal command-prefix match, so a command that *starts* with an env-var assignment (`TEST_DATABASE_URL=… bun test`) does not match a `Bash(bun:*)` rule — the assignment is part of the matched string. Setting `TEST_DATABASE_URL` as step `env:` sidesteps this entirely rather than requiring the agent to type it inline. **(5) All setup steps (mise, `bun install`, `docker compose up`) are `continue-on-error: true`** — an advisory review must degrade to "fewer working Bash tools", never to "no review", so a lockfile drift that `unit` already fails on cannot also silently swallow the review; each job ends with an unconditional `docker compose down -v` (`if: always()`) so a denied or wedged run never leaves containers on the shared runner. **(6) Neither workflow can review a PR that edits it**: the OIDC → App-token exchange refuses to issue a token when the workflow file on the PR branch differs from the copy on the default branch, and the action self-skips with "workflow validation failed" — so changes here are verified locally (`nektos/act`, `actionlint`) or on the first PR after merge.

The reviewer also skips bot senders, which in this repo means docs-sentinel's doc-fix commits (a push from the bot suppresses the re-review for *that* push). The `chore(release): version packages` PR never reaches it at all — a `GITHUB_TOKEN`-opened PR fires no `pull_request` workflows, the same fact that leaves that PR without CI checks.

## Known residuals (documented, deliberate)

Single-writer-per-hash world constraint (proper world-factory patch tracked; safe in the shipped single-worker prod compose) — and the agents-first pivot makes it HOTTER: all of an agent's chat sessions plus every workflow `agent` step delegating to it concentrate on its one published version hash (one world DB, one writer — also why `for_each` runs at concurrency 1) · Slack reply delivery is at-least-once (the `chat.postMessage` lands before the `delivery_status` marker settles — a crash in between re-posts the reply on boot recovery; the marker itself is CAS'd) — and pipeline `tool` steps share the stance: an `at_least_once` step interrupted in its crash window re-executes on replay (`sideEffect:"at_most_once"` is the opt-out, failing `interrupted` instead) · turn attribution is by content (`runs.message_hash` vs the turn's `message.received`), so its one residual is IDENTICAL text sent twice on one session — a never-sent canceled run whose text equals a successor's can still claim the successor's turn (oldest matching obligation wins; a successor's message reaching eve after a later one, only possible in the timeout-races-202 window, surfaces the same way as a foreign turn) — and content-less HITL turns (an `inputResponses` resume echoes no `message.received`) fall back to send order among content-less senders only · agent-step child dispatch has one irreducible crash window: eve session ids are server-minted (202 create), so every dispatch path CAS-writes a dispatch-attempt marker (`runs.started_at`) strictly before the eve call and the marker — never the session's possibly pre-existing eve id — is the recovery authority: boot reconciliation refuses to tail a marker-null run (nothing was sent; it fails the child, and the agent step's stillborn recovery re-dispatches on replay — a fresh child, or a re-sent `session:"thread"` continuation into the same session — never a double dispatch), but the window BETWEEN the marker write and the eve-session-id persist is undecidable — a crash there, and equally an eve call that FAILS after arming (a client-side timeout can race eve's 202): the run fails honest (`agent_run_failed` for an agent-step child, failing the workflow), the still-eveless session is closed (boot reconciliation for a crash — or the next lock-holding dispatch on it, which heals the abandoned row inline; `failEveDispatch` immediately for a failed call — on ANY terminal outcome, freeing its thread claim so the next message mints a fresh session instead of a second live turn on the poisoned row), and if eve did accept the create, that turn runs to completion unobserved — side effects happen at most once, and nothing re-dispatches it (a Stop's remote leg, by contrast, is never lost: it is recorded on the run as `remote_cancel_pending_at` — written INSIDE the same CAS that settles the row canceled on every path, the live tail's finalize included, never as a second statement after it — and met only by eve's own stream: the run's turn boundary after its own `turn.started`, a session-terminal answer, or a NEWER run whose `turn_id` is set;
